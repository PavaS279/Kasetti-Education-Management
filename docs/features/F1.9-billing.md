# F1.9 — Invoices, payments, allocation and reconciliation

**Status:** ✅ Built · ✅ Deployed · ✅ Unit tested · ✅ End-to-end checked (2026-10-03)

Custom billing ledger per [ADR-002](../adr/ADR-002-custom-billing-ledger.md). All ledger fields are system-managed: totals change only through `BillingService`, and every write needs the **KEM Manage Billing** custom permission (Administrator, Finance, Branch Manager).

## What it does

| Capability             | How                                                                                                                                                                                                                                                        |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Invoice from enrolment | `createInvoice(enrolment, issueNow)` copies the uninvoiced `Enrolment_Fee_Line__c` rows (the price agreed at enrolment, never the live price list) to `Invoice_Line__c` and marks them invoiced. Blocked while a discount awaits approval                  |
| Bill-to                | The learner's active **fee-paying guardian** (`ContactContactRelation.Is_Fee_Payer__c`), otherwise the learner                                                                                                                                             |
| Numbering and dates    | `<branch prefix>-<sequence>` (for example `BLR-000001`); issue date today, due date from the branch's invoice due days (`BranchPolicy`, org default 14)                                                                                                    |
| Totals                 | Roll-ups: subtotal, discount, tax, total from lines; amount paid from allocations; balance due and overdue are formulas                                                                                                                                    |
| Statuses               | Invoice Draft → Issued → Partially Paid → Paid, or Cancelled (governed by `Status_Transition__mdt`). Enrolment `Billing_Status__c`: Not Invoiced / Invoiced / Partially Paid / Paid                                                                        |
| Cancel                 | Draft or unpaid issued invoices only, with a reason; fee lines are released so the enrolment can be invoiced again                                                                                                                                         |
| Payments               | `Student_Payment__c`: amount, method (Cash, UPI, Card, Bank Transfer, Cheque, Online Gateway), reference, date. Confirmed now, or **Pending** until funds clear (confirm / mark failed)                                                                    |
| Idempotency            | `Gateway_Transaction_Id__c` is unique: a repeated notification returns the original payment, including when two arrive at the same time                                                                                                                    |
| Allocation             | On confirmation: first the invoice paid for, then the payer's other open invoices **oldest due first** (rows locked). `Payment_Allocation__c` junction rolls up to both sides                                                                              |
| Receipts               | `RCT-<payment number>` issued when the payment is confirmed                                                                                                                                                                                                |
| Reconciliation         | Fully allocated → **Reconciled** (who/when stamped). Remainder → **Exception** with a note. Resolve: retry allocation (for example after a new invoice), or close with a settlement note (refund/credit). Failed payments close as reconciled, unallocated |
| Ledger protection      | Issued invoices cannot be deleted (cancel instead); confirmed payments cannot be deleted or moved back to pending                                                                                                                                          |
| Gateway API            | `POST /services/apexrest/kem/v1/payments` `{transactionId, invoiceNumber, amount, status: success\|pending\|failed, method, paidOn}` → 201 created, 200 duplicate, 400 invalid. A later `success`/`failed` moves a pending transaction on                  |

## User interface

- **Class roster**: row action **Create invoice** (shown to billing users for enrolments not yet invoiced and without a pending discount) issues the invoice and opens it.
- **Invoice record page** (`KEM_Invoice_Record_Page`, app override) with **`kemInvoice`**: hero with number, status, overdue flag, issue/due dates, total/paid/balance and an animated paid-progress bar; bill-to and learner cards; charges table with discount and tax; payments timeline with receipt numbers; _Awaiting confirmation_ list with Confirm / Failed; actions _Issue invoice_, _Record payment_, _Cancel invoice_ according to status and permission.
- **`kemPaymentModal`**: amount defaulting to the balance, method, reference (required except cash), date, _Funds received_ toggle (off by default for cheque and bank transfer), overpayment warning.
- **Finance Desk** tab (`kemFinanceDesk`): KPI cards (outstanding, overdue, collected this month) and work queues — awaiting confirmation, reconciliation exceptions (retry / close with note), overdue invoices with age badges, recent receipts.
- **Learner 360**: **Fees** tab with balance due, overdue count and the learner's invoices (visible to users who can see invoices).

## End-to-end check in the org (2026-10-03)

Demo family (guardian Rohit is the fee payer):

1. Invoices **BLR-000001** (Ananya, 16,520) and **BLR-000002** (Arjun, 15,281, sibling discount) issued to Rohit, due in 15 days (branch policy); enrolments → Invoiced.
2. Cash 5,000 on BLR-000001 → receipt, reconciled; invoice and enrolment → Partially Paid.
3. Real HTTPS calls to `/kem/v1/payments`: `pending` 11,520 → **201** Pending; `success` → **201** Confirmed, reconciled, BLR-000001 **Paid**; replay → **200** duplicate; unknown invoice → **400**.
4. Bank transfer 16,281 from Rohit with no invoice → 15,281 allocated to BLR-000002 (**Paid**), 1,000 → **Exception** (shown on the Finance Desk); closed with a credit note → Reconciled.
5. Final: both invoices Paid, both enrolments Paid, outstanding 0, collected 32,801 = 5,000 + 11,520 + 16,281, no exceptions or pending payments.

## Notes

- Payment numbers started at `PAY-000000` (auto-number default start); harmless, left unchanged to avoid altering an existing production auto-number.
- A payment closed with a credit note keeps its unallocated amount on the record for audit; it is not applied automatically to later invoices.
