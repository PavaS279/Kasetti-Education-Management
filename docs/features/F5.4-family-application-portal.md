# F5.4 — New family, New application and Give portal access

**Status:** ✅ Built · ✅ Deployed · ✅ Unit tested · ✅ End-to-end checked (2026-10-07)

Phase 5 stage 4 covers the people screens: a family who walks in ready to join, an application for a learner already on file, and a portal login sent straight to a parent. The last one follows the decision that the button sends the welcome email at once.

## New family (walk-in) (`kemFamilyModal`)

Opened from **Admissions → Enquiries** (`kemEnquiryPipeline`) with **New family (walk-in)**, next to New enquiry. Use it when a family is ready to join and needs no enquiry.

1. **Parents:**
   - Branch, which defaults to the person's first branch role, and the address.
   - Each parent: name, relationship, email and mobile (one of them is required), language, preferred channel, and **Pays the fees**. Only one parent can be ticked; if nobody is, the first parent pays.
   - An empty parent is skipped, and **Add another parent or guardian** adds one.
2. **Children:**
   - Each child: name (the parents' last name is filled in), date of birth (required, because course eligibility uses it) and school.
   - A **Next step** for each child:
     - **Just add**.
     - **Enrol in a class now**: open classes at the branch with free seats; a course can be chosen first to narrow the list.
     - **Start an application**: for a course.
3. **Check and save:**
   - Before anything is saved, the screen looks for people already on file:
     - a parent with the same email, or with the same last name and mobile;
     - a child with the same name and date of birth.
   - **Use existing** keeps one record per person. Their role is merged; for example, a learner who is now also a parent becomes _Learner and Guardian_.
   - A summary line follows, such as "2 parents · 2 children · 1 already on file · 1 enrolled now · 1 application", then **Save the family**.

**What is saved, all together or not at all:**

- Person accounts with the branch and address, the language and channel for parents, and the school for children.
- Every parent linked to every child as guardian, with the fee payer, emergency contact and portal flags.
- Each enrolment, through the normal enrolment rules: seats, price, agreed price and fee lines.
- Each application at _Processing_, with its document checklist and age eligibility.

If any of these fails, for example because a class filled up in the meantime, nothing is saved and the reason is shown. Afterwards the first child's Learner 360 opens.

## New application (`kemApplicationModal`)

Opened from **Learner 360 → Applications → New application**.

- Choose the branch, course and preferred class; only the course's open classes are offered.
- The application starts at _Processing_ with its checklist and eligibility.
- A second open application for the same course is refused, and so is an application for someone who is not a learner.

## Give portal access (`kemPortalAccessModal`)

Opened from **Learner 360 → Portal access**, or from the Set-up Centre portal tile (**Give portal access**, which starts with a search).

**The screen:**

- Lists the person's family two steps out: parents, children and siblings.
- Shows each person's login status (has a login, deactivated, or none) and username.
- Gives the reason when a login cannot be given: no email, under 13 (they use a parent's login), or no free licence.
- Shows the free portal licences and the portal address.

**Give access:**

1. If the family's record owner has no role (a Salesforce rule for portal users), the record is first moved to an administrator who has one. This runs as a separate step.
2. The login is created:
   - Profile _EDC Community User_, Indian locale.
   - The Education Cloud experience licence (`EducationCloudExprcCloudAccessPsl`) and **KEM Portal User**.
   - Username: email + `.kasettitechnologiespvtltd.portal`.
3. **The welcome email with the link to set a password is sent at once.**

Parents then see every child they are linked to with portal access (F2.8).

New families are created with an administrator who has a role as owner when the person adding them has no role, so portal access works without moving them later.

## Access

| Screen                                                | Administrator | Branch Manager | Admissions Counsellor | Others |
| ----------------------------------------------------- | ------------- | -------------- | --------------------- | ------ |
| New family, New application (`FamilySetupController`) | ✅            | ✅             | ✅                    | —      |
| Give portal access (`PortalAccessController`)         | ✅            | ✅             | ✅                    | —      |

Giving portal access needs two permissions, now in the KEM Administrator, KEM Branch Manager and KEM Admissions Counsellor permission sets:

- the new **KEM Manage Portal** custom permission;
- Salesforce's **Manage External Users** (`ManagePartners`). Salesforce requires it to create portal users. It does not open Setup, because these personas have no Setup access.

People without them see the family's status and a note to ask an administrator. Families save in user mode. The duplicate check reads in user mode. Portal logins, licences and permission assignments are created in system mode, but only after the permission check.
