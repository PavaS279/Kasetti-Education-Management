# F1.3 — Applications: checklist, eligibility, review, decision, offer

**Status:** ✅ Built · ✅ Deployed · ✅ Unit tested · ✅ End-to-end checked (2026-10-03)

## What it does

| Capability         | How                                                                                                                                                                                                                                                                                                                                       |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Application record | Native `IndividualApplication` (Admissions record type) created by enquiry conversion or manually                                                                                                                                                                                                                                         |
| Checklist          | On insert, one `DocumentChecklistItem` per active `Application_Checklist_Item__mdt` row (Birth Certificate, Photo Identity, Address Proof required; Report Card, Passport Photo optional). Files upload directly onto each item. `Checklist_Complete__c` is maintained when items change                                                  |
| Eligibility        | Age at application vs `LearningCourse.Minimum_Age__c` / `Maximum_Age__c` → Eligible / Not Eligible / Not Checked (no birthdate); re-evaluated when course or learner changes. Override requires the **KEM Override Eligibility** custom permission (permission set `KEM_Eligibility_Override`) and a reason, stamped with the user's name |
| Review             | Processing → In Review (reviewer assigned) → Ready For Decision (requires complete checklist and eligibility) ; In Review → Processing returns to applicant                                                                                                                                                                               |
| Decision           | Admit / Waitlist / Reject (reason mandatory for waitlist and reject), decider and timestamp recorded                                                                                                                                                                                                                                      |
| Offer              | Admit creates an offer (`Offer_Status__c = Offered`, expiry from `Offer_Validity_Days` setting or per decision); acceptance/decline recorded; expired offers cannot be accepted                                                                                                                                                           |
| Offer expiry       | `OfferExpiryJob` (batch + schedulable) runs nightly 01:30 as **KEM Offer Expiry**                                                                                                                                                                                                                                                         |
| Withdrawal         | Any open application, reason required                                                                                                                                                                                                                                                                                                     |
| Governance         | `Status` and `Offer_Status__c` transitions declared in `Status_Transition__mdt`; decision/offer/eligibility fields are system-managed (users cannot edit them directly; services check record edit access with `UserRecordAccess`)                                                                                                        |

## User interface

- **Admissions Review tab** (`kemApplicationQueue`): columns Processing / In review / Ready for decision / Offer out, branch filter, KPI counts, keyboard-accessible cards with checklist, eligibility, and offer-expiry badges.
- **Application record page** (`KEM_Application_Record_Page`) with **`kemApplicationWorkbench`**: animated checklist progress ring, stage path, stage-specific actions, per-item accept/reject/waive/reset with file upload, add item, eligibility card with override, decision card, offer card with expiry countdown.
- Modals: `kemDecisionModal` (choice cards + validity days + reason), `kemReasonModal` (generic reason capture).

## End-to-end check in the org (2026-10-03)

Created demo course `[KEM Demo] Mathematics Foundation` (ages 8–16, `KEM-DEMO-MATH`), set the demo learner's birthdate, attached the course to application `IA-0000000032` → **Eligible (age 12)**; generated the checklist and accepted/waived all 5 items through the **real** `DocumentChecklistItem` update path → checklist complete; submitted → ready → **Admit** (14-day offer) → **offer accepted**. `KEM Offer Expiry` job scheduled.

Defect found and fixed during the check: applications created before this feature had a blank offer status, so `null → Offered` was rejected; transitions now treat a blank legacy value as _Not Offered_ (unit-tested).

## Operations

- `scripts/deploy.sh` pauses `KEM *` scheduled jobs before deploying and re-schedules them afterwards (`KemJobs.scheduleAll()`), because production blocks deploying classes that scheduled jobs depend on.

## Checklist files and family uploads (2026-10-06)

- **Staff:** every checklist item keeps **Upload Files**, and lists the files already received with who sent them and when, a **From portal** tag for files sent by the family, and a **View** button that opens the Salesforce file preview. The application page's right-hand column shows the **Files** list; the standard Document Checklist Items, Application Reviews and Application Decisions lists (duplicates of the workbench or unused) were removed from the layout.
- **Family portal (upload only):** _My Learning_ shows **Admission documents** for each open application of the family's learners: each item with Required, its status (Not uploaded yet, Sent – awaiting review, Please upload again with the staff reason, Accepted, Not needed) and a file picker (PDF, JPG or PNG up to 3 MB) while the item is open. Families cannot accept, reject or waive, and cannot replace an accepted or waived item.
- **How it works:** the portal saves the file and publishes `Admission_Document__e`; its trigger, running as the Automated Process user (portal licences cannot change checklist items), links the file to the checklist item and sets it to **Pending** for staff review. Staff then accept or reject as before.
- **Tests:** `PortalServiceTest.familiesUploadAdmissionDocumentsForReview` (portal user sees open items, refusals for decided items, wrong file type, empty file, a non-checklist record and another family; upload, event, Pending, staff view; a late event for an accepted item changes nothing). Jest: workbench file list and View; portal card has only file pickers. Live: Address Proof on IA-0000000041 went New → Pending with the file shown to staff.
