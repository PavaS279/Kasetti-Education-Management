# F3.2 — Scale and performance

**Status:** ✅ Built · ✅ Deployed · ✅ Unit tested · ✅ End-to-end checked (2026-10-05)

Phase 3 adds centres and volume. This feature measures the background work and fixes the parts that would have broken at multi-centre volumes.

## What was measured

| Path                             | Cost                                                                         | Problem at volume                                                                                                       |
| -------------------------------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Recurring billing, per enrolment | 18 queries, 8 DML statements, ~150 ms CPU (measured in the org, rolled back) | Batches of 20 need ~360 queries, but background jobs allow 200: a night with 12+ enrolments due in one batch would fail |
| Payment reminders                | 2–4 queries per run                                                          | Capped at 2,000 invoices per run; anything beyond was silently not reminded                                             |
| Email delivery                   | 100 emails per job                                                           | Hourly job plus event triggers ≈ 2,400 emails a day at most; reaching the daily email allowance marked email **Failed** |

## Changes

**Recurring billing (`RecurringBillingJob`)**

- Batch size from Education Setting `Recurring_Billing_Batch_Size` (default **5**, about 90 queries of the 200 allowed).
- Before each enrolment the job checks the remaining query, DML and CPU headroom (using the largest cost seen so far, at least 25 queries, plus 20%). An enrolment that does not fit is left for a **follow-up run**, which starts automatically when the batch finishes, while runs make progress (at most 10 passes). The finish log reports invoices raised, failures and enrolments left for the follow-up run.
- Scheduled job and console **Run now** both use `RecurringBillingJob.run()`.

**Payment reminders (`ReminderJob`, new)**

- A batch over every open invoice with a balance due on a reminder date (due soon, and each overdue reminder day), 200 per batch, no cap.
- `MessageService.remindInvoices(ids, today)` does the work in a fixed number of queries and one insert per batch; duplicates are still prevented by the message dedup key.
- When the batch finishes it starts email delivery. `KEM Payment Reminders` (daily 09:05) and **Run now** start the batch; the console's background runs include it.

**Email delivery (`MessageService.dispatch`, `DispatchJob`)**

- Sends no more than the org's remaining daily single-email allowance (`OrgLimits` SingleEmail). When it is used up, email **stays Queued** (a warning is logged) and goes out after the allowance resets, instead of being marked Failed.
- A delivery job that sends a full round of 100 and finds more queued email starts the next round, up to Education Setting `Dispatch_Rounds` (default 20) in a row (2,000 emails).

## Query selectivity

- Branch comparison, Home insights and the operations console use aggregate queries; their query count does not grow with data volume (measured below).
- Background queries filter on indexed fields where possible: lookups (branch, class, enrolment, invoice), external IDs and unique keys (`Dedup_Key__c`, `External_Id__c`), and record IDs.
- Large-volume candidates for custom indexes (request from Salesforce Support when a table passes ~100,000 rows): `Student_Invoice__c.Due_Date__c`, `Message__c.Status__c`, `Enrolment_Fee_Line__c.Next_Bill_Date__c`, `Class_Session__c.Start__c`.

## Tests (`VolumeTest`)

| Test                                                        | Asserts                                                                                   |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Reminder batch covers every invoice due                     | 200 invoices due in 3 days → 200 due-soon portal notices through `ReminderJob`            |
| Reminders use a fixed number of queries                     | 200 overdue invoices → at most 15 queries and 5 DML statements; a second run creates none |
| Recurring billing leaves work for a follow-up run           | No headroom → every enrolment deferred, none billed; default batch size 5                 |
| Dispatch keeps email queued when the daily limit is reached | Delivery live, allowance 0 → nothing sent, message still Queued                           |
| Session triggers handle 200 records                         | Insert and update of 200 sessions in at most 20 queries                                   |
| Enquiry triggers handle 200 records                         | 200 enquiries (assignment, duplicate checks) in at most 30 queries                        |
| Branch comparison uses aggregates                           | 50 branches in at most 10 queries                                                         |

Existing tests (`MessageServiceTest`, `RecurringBillingTest`, `OpsServiceTest`) cover the reminder content, billing results and run-now for the changed jobs.
