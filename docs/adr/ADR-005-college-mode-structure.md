# ADR-005 — College mode: structure, billing anchor, versioned rules and results

- **Status:** Accepted (2026-10-13, after the C0 consistency review; proposed the same day) — C0 technical architecture in [COLLEGE-DESIGN.md](../COLLEGE-DESIGN.md) version 2. Documentation only; nothing built.
- **Context:** The solution was demonstrated for after-school learning centres (short courses, monthly fees, age-based eligibility, parent-paid, one teacher per class, one grade per class). The institution needs a college model for two campuses (Yelahanka, Rajajinagar), each running PUC (4 branches), Diploma (3) and BE (4), with cut-offs that differ by branch, entry route and year, a Dean interview, yearly fees paid by DD, cheque or online only, roll numbers, lateral entry from Diploma to BE Year 2, many subjects and faculty per section, and subject-level results. A review of version 1 found that global relabelling, an undecided programme enrolment, invoice-before-enrolment billing, single-exam rules, missing seat control, and the class-level teaching and grading model would not work with the existing implementation.
- **Decision:**
  1. **No global relabelling.** Object labels stay. College words (Campus, Programme, Branch, Section, Subject) appear only in the KT College app, its record-type pages, custom labels and LWC text. College behaviour is selected by `Branch__c.Institution_Type__c` and record types (`College_Branch`, `College_Section`, `College_Admission`).
  2. **Custom `Programme_Enrolment__c`** (not standard `ProgramEnrollment`) is created **Provisional** when the Dean admits, and is the **billing anchor**: invoices and fee-line snapshots link to it; section enrolments (`CourseOfferingParticipant`) link to it per academic year. Lifecycle: Provisional → Enrolled → Completed / Discontinued; Provisional → Expired (payment window) / Cancelled.
  3. **Roll number** (`KT` + year + campus + programme + branch + serial; regular 001–400, lateral 401–999) is issued from a locked sequence when the programme's release rule holds; the demo rule is _full annual invoice paid_ = confirmed-payment and authorised-credit allocations clear the invoice balance.
  4. **Admission rules are immutable versions** (unique version key; at most one Active version per logical rule through a unique active key; campus-specific beats all-campus). Accepted entrance exams are child records (any one passes). Each admission stores the exact version and evidence it was evaluated against. Eligibility override stays `KEM_Override_Eligibility`, Dean-only.
  5. **Run-time configuration is custom objects** (campus branches, rules, document rules, fees); `Application_Checklist_Item__mdt` stays for learning centres.
  6. **Seat reservations** (Reserved → Finalised / Released / Expired) are idempotent and audited, and every transition locks the campus-branch intake record.
  7. **Teaching and results:** `Section_Subject__c` (section, subject, term, faculty, room, marks configuration) carries the timetable and assessments. Results form the hierarchy section enrolment → section subject → subject result → assessment results, with term results above them. Dean finalisation locks published results; reopening is Dean-only with a reason. The existing class-level grade services skip college sections.
  8. **Portal access** uses the ADR-003 allowed-learner resolution (student, or active guardian link) with no record sharing; files are uploaded and downloaded only through Apex checks; Identity documents are deleted after verification.
- **Consequences:** 13 new objects (7 from version 1 plus 6 additional) and additive fields on 15 existing objects. Learning-centre behaviour is unchanged by construction (campus type and record type guards); the existing regression suite must still pass, with results recorded as evidence in TEST-LOG.md. Cut-offs, fees, documents and intake change every year without deployment, and past decisions remain explainable. A student keeps one person record across PUC → Diploma → BE, with one programme enrolment and roll number per programme. Before C1 deploys, the implementation checks in COLLEGE-DESIGN.md §14 (standard-object extensibility, Experience Cloud licensing, metadata behaviour, allocation timing) must pass; a failed check reopens this ADR.
